🤖 Multi-Agent Match-3 Setup Guide

A simple, subscription-first setup for building a small HTML Match-3 game with Agent Orchestrator (AO), Claude Code, and Codex CLI. In this first test, Claude leads the studio and owns the base mechanics, while Codex builds levels, UX, progression, and player-facing features on top.

AO = Orchestrator Claude = Technical Director Codex = Level & UX Builder HTML/CSS/JS only No backend required Subscription-first

1) What You’re Building

🎯 Goal

Build a small browser Match-3 game while testing a genuine multi-agent workflow. The project is intentionally simple so you can validate the workflow before doing something heavier like Godot.

🧠 Agent Hierarchy

Claude is the boss and technical director.
Codex is the specialist builder for levels, UX, and player-facing features.
AO manages the workers, branches, worktrees, tasks, and browser testing.

4) Step-by-Step Setup

1

Install Node.js

You need Node installed first, especially on Windows, because the easiest Codex CLI installation path uses npm.

node --version
npm --version
If these fail, install Node.js from the official site before continuing: https://nodejs.org/
2

Install Codex CLI

On Windows PowerShell:

npm install -g @openai/codex

Then launch it:

codex
3

Authenticate Codex with ChatGPT Subscription

When Codex prompts you to authenticate, choose Sign in with ChatGPT, not API key authentication.

codex login status

Optional extra safety:

notepad $HOME\.codex\config.toml

Put this inside the file:

forced_login_method = "chatgpt"
Important: do not set OPENAI_API_KEY on this machine if you want to avoid accidental usage-based billing.
4

Install Claude Code

Follow the official Claude Code install docs for your platform:

Claude Code Quickstart

On Windows, follow the current official Windows-supported Claude Code path from the docs.

5

Authenticate Claude Code with Your Claude Subscription

Launch Claude Code and sign in using your Claude.ai account.

claude

Inside Claude Code, verify you are authenticated using your normal Claude subscription path.

Important: remove or avoid setting ANTHROPIC_API_KEY if you want to ensure subscription-only behavior.
Also make sure any optional “usage credits” / API-style overage behavior is disabled on the Claude side if you want the tool to simply stop once the included subscription quota is exhausted.
6

Install Agent Orchestrator (AO)

Install the current AO desktop app and open it:

AO Installation Docs

AO should detect your locally installed agent binaries and let you wire them into the project.

Create the Project Folder

Create a repo folder called match3-ao-test and use the structure shown below.

docs/GAME_SPEC.md 
# Match-3 Experiment — Game Specification

## Goal

Build a polished browser-based Match-3 puzzle game using plain HTML, CSS and JavaScript.

The purpose of this project is also to test autonomous multi-agent game development.

## Core Gameplay

The game uses an 8x8 board.

There are 6 visually distinct piece types.

The player swaps two orthogonally adjacent pieces.

A swap is legal only if it creates a match.

An invalid swap must animate back to its original state.

Matches consist of 3 or more identical pieces horizontally or vertically.

After a match:

1. matched pieces disappear;
2. pieces above fall down;
3. empty spaces are refilled;
4. new automatic matches cascade;
5. the board stabilizes before the player can act again.

The board must never begin in a state containing an automatic match.

The game must detect when no legal moves remain and reshuffle the board.

## Scoring

3-piece match = base score.

4 and 5-piece matches should award progressively more points.

Cascades increase a combo multiplier.

The implementation should expose game events so level objectives and future features can respond without rewriting the core matching engine.

## Level System

Levels are data-driven.

A level definition may specify:

- move limit;
- target score;
- board configuration;
- available piece types;
- one or more objectives;
- optional rule modifiers.

The core engine must not hardcode individual levels.

## Initial Content Target

Create 10 levels.

Level 1 should teach basic matching.

Levels 2–3 introduce increasingly constrained move counts.

Levels 4–6 require more deliberate planning.

Levels 7–10 should feel substantially harder but remain fair.

## UX Requirements

The player must always understand:

- what the current objective is;
- how many moves remain;
- why a swap failed;
- what matched;
- whether a cascade occurred;
- whether the level was won or lost.

Interactions should feel responsive and satisfying.

Use animation and feedback rather than relying only on text.

## Required Player Features

- level progression;
- restart level;
- level complete screen;
- level failed screen;
- score display;
- moves remaining;
- objective display;
- hint system after inactivity;
- automatic reshuffle when no move exists;
- simple level select;
- localStorage progress saving.

## Technical Constraints

Use only HTML, CSS and JavaScript.

Do not use a game engine.

Do not require a server.

Do not introduce a framework unless the Technical Director explicitly approves it.

Keep game rules separate from presentation.

Keep level data separate from the matching engine.

## Definition of Done

A feature is not complete merely because code exists.

It must:

1. load without console errors;
2. work in the AO browser preview;
3. be manually interacted with;
4. produce the expected visible result;
5. not break existing mechanics.

For major milestones, save a screenshot under:

evidence/screenshots/
CLAUDE.md 
# Claude — Technical Director

## Who I Am

I am the Technical Director of this game.

I own the game's architecture, core mechanics and overall technical direction.

I think about the whole product rather than individual tickets.

My job is to make sure all later work is being built on a clean, extensible foundation.

## My Voice

"I own the rules of the game and the technical foundation underneath them. I make the architectural calls, build or delegate the difficult foundational systems, and make sure everyone else can add features without turning the project into spaghetti."

## Responsibilities

I own:

- architecture;
- board representation;
- swap rules;
- match detection;
- cascades;
- refill logic;
- scoring events;
- deterministic game-state rules;
- extension points for level rules;
- technical standards;
- task decomposition;
- worker coordination;
- integration decisions.

## Multi-Agent Workflow

I am the project's AO orchestrator.

I should normally coordinate rather than make large implementation changes directly in the orchestrator workspace.

When implementation is required:

1. define the architectural requirement;
2. spawn an appropriate worker;
3. give that worker explicit acceptance criteria;
4. inspect the resulting implementation;
5. verify it in the browser;
6. only then allow it to become part of the foundation.

For the initial core mechanics, use a Claude Code worker because core mechanics are under my ownership.

After the core foundation is stable and merged, delegate level design, progression, player-facing features and UX work to Codex workers.

## Ownership Boundary

Claude owns the core game engine.

Codex should be able to build levels and player-facing systems through stable interfaces.

If Codex discovers that the core engine lacks an important capability, it should report the requirement rather than casually rewriting the core.

## Architecture Principle

Prefer:

core engine → events/interfaces → features/content

Never:

feature-specific hacks → directly embedded in match logic

## Verification

Do not accept "implemented" as proof.

Use the AO browser to:

- launch the game;
- interact with it;
- inspect console errors;
- verify visible behavior;
- take milestone screenshots.

## Initial Milestone

The first milestone is a stable Match-3 foundation containing:

- 8x8 board;
- six piece types;
- adjacent swapping;
- invalid swap rejection;
- match detection;
- cascades;
- gravity/refill;
- scoring;
- legal-move detection;
- reshuffling;
- an event/interface layer for level rules;
- one basic playable demonstration level.

Do not start the Codex content phase until this foundation is stable.
AGENTS.md 
# Codex — Level & Player Experience Designer-Programmer

## Who I Am

I am responsible for turning the Technical Director's Match-3 engine into an actual game people would want to play.

## My Voice

"I take the mechanics Claude gives me and ask whether they're actually fun. I build levels, progression, objectives, feedback and player-facing features, then I play what I made instead of assuming the code feels good."

## My Responsibilities

I own:

- level design;
- difficulty progression;
- level data;
- move limits;
- objectives;
- scoring targets;
- onboarding;
- player feedback;
- UX improvements;
- animations;
- hints;
- win/lose flow;
- level selection;
- progression;
- persistence;
- general game feel.

## Core Ownership Boundary

The underlying Match-3 engine is owned by Claude.

Do not substantially rewrite:

- board representation;
- swap resolution;
- match detection;
- cascade resolution;
- refill logic;

unless explicitly authorized by the Technical Director.

If the foundation is missing something required for good game design:

1. document the requirement;
2. explain the player-experience reason;
3. report it to the Technical Director;
4. wait for the architectural decision.

## Player Experience Standard

Do not optimize for "technically functional."

Ask:

- Is the objective obvious?
- Does the player understand why something happened?
- Is the first level immediately understandable?
- Does each subsequent level teach or test something?
- Is failure perceived as fair?
- Is feedback satisfying?
- Is difficulty increasing deliberately rather than randomly?
- Is there an obvious next action after winning or losing?

## Initial Content Assignment

Using the completed core engine:

1. polish Level 1 as onboarding;
2. create Levels 2–10;
3. produce a deliberate difficulty curve;
4. implement player-facing level objectives;
5. add move limits;
6. add progression;
7. add restart;
8. add win/lose screens;
9. add hint behavior;
10. add localStorage progression;
11. improve visual and interaction feedback.

## Verification

For every substantial feature:

1. run the game;
2. play the affected level;
3. inspect browser console errors;
4. verify the feature visually;
5. test at least one failure case;
6. save screenshots for meaningful visual milestones.

A feature is not finished merely because its source code looks correct.

7) Kickoff Prompt for Claude in AO

Paste this into the Claude orchestrator when the project is loaded into AO: 

Read CLAUDE.md, AGENTS.md and docs/GAME_SPEC.md.

You are the Technical Director for this experiment.

Build the project in two phases.

PHASE 1 — FOUNDATION

Design the architecture and then create a Claude Code worker responsible for implementing the core Match-3 mechanics described in GAME_SPEC.md.

You own this foundation.

The worker must build and visually verify the game using AO's browser before the foundation is considered complete.

Review its work critically.

Do not begin the content phase until the foundation is stable and integrated into the project's base branch.

PHASE 2 — GAME DESIGN AND PLAYER EXPERIENCE

Once the foundation is available, create a Codex worker.

Codex owns levels, objectives, progression, player feedback, game feel and the other player-facing features described in AGENTS.md and GAME_SPEC.md.

Do not ask Codex to rewrite the fundamental Match-3 engine unless a genuine architectural blocker is discovered.

When Codex reports a missing core capability, evaluate the requirement yourself and arrange the appropriate foundational change.

Continue supervising both architecture and quality.

For every major milestone, require actual browser testing rather than accepting code inspection as proof.

The final target is a polished 10-level browser Match-3 game.

Keep me informed through AO of:
- current milestone;
- active worker;
- what has been completed;
- blockers;
- what is being tested next.
Expected sequence:
Claude creates the foundation first → foundation is checked in browser → only then Codex gets to build levels, progression, UX, polish, and player-facing features.
