🤖 Pulse Arena
Cline + Kanban + Godot Multi-Agent Setup

A Windows-first, subscription-first setup for a three-agent Godot arena-FPS project. You keep the repository open in VS Code with Cline, while Cline Kanban launches three isolated workers in parallel: Claude for core gameplay/bot AI, Codex for arena/UX/playtesting, and Claude for 3D art/polish.

So VS Code is your main editor/control desk, while npx kanban opens the parallel-agent board locally in your browser. This guide deliberately uses that split.

1. The architecture you are actually testing

This avoids the failure mode you saw with AO: no prompt is trusted to “maybe spawn” another agent. You explicitly create three Kanban cards and start all three. Kanban creates a separate Git worktree and terminal for each card, so the workers are genuinely separate processes and contexts.

2. Your three workers

Agent 1 — Core Gameplay & Bot AI Lead

Claude Code · Claude subscription

“I own the part that must feel right. I build the player, weapons, damage model and bot brain, keep the architecture clean, and I am the person who says whether the merged game is technically healthy.”

Agent 2 — Arena Systems, UX & Playtest

Codex CLI · ChatGPT subscription

“I make the combat loop into a game. I build arena flow, pickups, scoring, HUD and test scenarios, then I actually run matches and hunt for boring spaces, bad spawns and confusing feedback.”

Agent 3 — 3D Art & Polish

Claude Code by default · same Claude subscription

“I make the prototype stop looking like programmer art. I build an original modular kit in Blender, establish materials and lighting, export clean assets, and polish the scene without hiding gameplay problems behind effects.”
Quota balancing: Agent 3 is provider-agnostic. If two concurrent Claude workers burn your Claude allowance too quickly, switch the art card to Codex. The role file and MCP workflow remain the same.

6. Give the agents eyes and hands: MCP setup

A. Godot MCP Runtime — required

This is the most important tool in the stack. It is a zero-footprint local MCP server: it can launch a stock Godot 4.x project, capture gameplay screenshots, simulate input, inspect visible UI/live scene state, run controlled GDScript against the running scene, and read debug output.

Godot MCP Runtime repository ↗

Claude Code project config: .mcp.json

{ "mcpServers": { "godot": { "command": "npx", "args": ["-y", "godot-mcp-runtime"], "env": { "GODOT_PATH": "D:/Tools/Godot/Godot.exe" } } } }

Replace the path with your actual Godot executable. Then launch Claude once in the repo and approve the project MCP server. Verify with claude mcp list.

Codex project config: .codex/config.toml

[mcp_servers.godot] command = "npx" args = ["-y", "godot-mcp-runtime"] startup_timeout_sec = 20 tool_timeout_sec = 120 [mcp_servers.godot.env] GODOT_PATH = "D:/Tools/Godot/Godot.exe"

Then run codex mcp list. Codex supports project-scoped MCP config in trusted repositories.

Cline VS Code config — optional but useful

In the Cline panel click MCP Servers → Configure → Configure MCP Servers and add the same mcpServers JSON block. This lets your manual Cline session in VS Code inspect the game too. The direct Claude/Codex Kanban workers still need their own harness configs above.

Verification test: ask each harness to call the MCP tool that returns Godot project info. Then ask it to launch the project and capture a screenshot. Do this before trusting the three-agent run.

B. Blender MCP — Agent 3 only

Use the established open-source Blender MCP bridge from ahujasid for direct object/material control and Blender Python execution. Agent 3 uses it to build modular assets, then exports GLB into the repository.

Blender MCP repository ↗

  1. Install the Blender MCP addon in Blender according to the repo instructions.
  2. Start/connect the addon inside Blender.
  3. Add its stdio MCP server to Claude Code using the repository's current command/config.
  4. Verify the agent can inspect the Blender scene and obtain a viewport screenshot before starting art production.
Do not enable external paid 3D-generation APIs by default. Blender MCP can call optional services in some configurations. For this experiment, keep Agent 3 on procedural/manual Blender operations so your only model spend remains inside your subscriptions.

C. Optional later: Context7

If Godot/Cline APIs change quickly, Context7 can supply fresh library docs through MCP, but it is not required for the first build. Do not add tools merely because they exist.

7. Rules, skills, and why both exist

Rules = always-on guardrails

Cline workspace rules live under .clinerules/. They are ideal for ownership, architecture constraints, and “run the game before claiming done.”

Skills = load only when relevant

Cline skills live under .cline/skills/<name>/SKILL.md. They are better for detailed workflows like runtime verification, arena playtesting, and Blender → Godot export because they do not need to consume every task's context.

The critical behavior is also repeated in AGENTS.md and CLAUDE.md, because Kanban may launch Codex/Claude directly rather than through the Cline VS Code extension.

Recommended merge discipline

  1. Finish and review each role card.
  2. Commit/merge one branch at a time through Kanban so conflicts are explicit.
  3. After all three are on main, start an Integration + Regression card using Agent 1.
  4. That card must run the combined game via Godot MCP, fight at least one bot, inspect errors, and capture a screenshot.
  5. Every failure becomes a new bounded card assigned to the owning role.
  6. Start the next milestone only after integration is playable.

What the integration card should say

Read AGENTS.md, docs/GAME_SPEC.md, docs/ARCHITECTURE.md and docs/OWNERSHIP.md. Act as integration owner. Do not add unrelated features. Run the merged game through Godot MCP Runtime and verify the current milestone end-to-end: spawn, move, acquire weapon, fight a bot, receive/deal damage, die/respawn, score a frag, inspect HUD, and inspect the current art pass. Capture evidence. Fix only integration/core issues inside Agent 1 ownership. For failures owned by Agent 2 or Agent 3, write precise follow-up card descriptions instead of absorbing their work.

How to get the screenshot-heavy progress report later

Require every card to follow docs/PROGRESS_PROTOCOL.md. Once the evidence directory has several milestones, a tiny local script can build the visual HTML dashboard you originally wanted from Git history + screenshots + test summaries. This is deliberately separate from Kanban: Kanban tracks worker state; the project dashboard tracks the game itself.

# Pulse Arena — Agentic Godot Experiment

A small original arena-FPS inspired by classic late-1990s arena shooters. It uses original names, maps, meshes, materials, sounds, and UI; do not copy Quake III assets, maps, logos, audio, or branding.

## Goal
Build a fast single-player arena shooter in Godot 4.x with bot enemies, responsive movement, several weapons, pickups, one polished arena, a score/match loop, and a repeatable agent-driven visual verification process.

## Team

- Agent 3 — 3D Art & Polish Artist-Engineer (Claude Code by default)

Each Kanban task runs in an isolated Git worktree. Agents only edit their owned paths unless an integration task explicitly grants broader access. Major work must be run in Godot and visually verified before it is considered done.

# Repository Instructions for Agents

## Project
This repository contains Pulse Arena, an original Godot 4.x arena-FPS experiment with bot enemies.

## Non-negotiable rules
1. Read `docs/GAME_SPEC.md`, `docs/ARCHITECTURE.md`, and `docs/OWNERSHIP.md` before editing.
2. Respect path ownership. Do not edit another agent's owned paths unless the task explicitly authorizes it.
3. Do not copy copyrighted Quake III assets, map geometry, names, logos, sounds, textures, or UI. Reproduce only broad arena-shooter mechanics using original content.
4. Prefer GDScript and stock Godot 4.x features. Add third-party dependencies only when explicitly approved.
5. Do not make gameplay logic depend on final art assets. Use stable data/resources and clear interfaces.
6. A feature is not done because it compiles. Run it, inspect runtime output, and capture evidence for meaningful milestones.
7. Keep `project.godot`, autoloads, input-map changes, and global architecture under Agent 1 ownership unless an integration task says otherwise.
8. Do not silently rewrite shared interfaces. If an interface must change, document the reason in the task output and update `docs/ARCHITECTURE.md`.

## Verification
For gameplay-facing work:
- Run the project through Godot MCP Runtime when available.
- Check debug output.
- Exercise the feature with simulated input where feasible.
- Capture at least one screenshot for major visual milestones.
- Test a failure/edge case, not only the happy path.

## Git / Kanban
- One Kanban card = one bounded deliverable.
- Each card should stay inside its worktree.
- Commit only after verification.
- Integration happens after parallel tasks are reviewed and merged to the base branch.

# Pulse Arena — Game Specification

## Product target
Create a believable, original arena-FPS prototype inspired by the responsiveness and readability of classic arena shooters. The first release is single-player against bots, not online multiplayer.

## Core player experience
The game should feel immediate, fast, readable, and skill-driven.

### Movement
- First-person mouse look.
- Responsive ground acceleration and friction.
- Air control sufficient to reward movement skill without requiring exact Quake physics emulation.
- Jumping and momentum preservation.
- Reliable stairs/slopes/collision behavior.
- Configurable FOV and mouse sensitivity.
- No camera bob that interferes with aiming.

### Combat
Initial weapon set:
1. Machine gun — reliable hitscan starter.
2. Shotgun — close-range burst with pellet spread.
3. Rocket launcher — projectile, splash damage, self-damage, knockback.
4. Rail-style precision weapon — high-damage hitscan with long recovery.

Weapon rules:
- Clear damage feedback.
- Distinct cadence, range, and tactical role.
- Predictable ammo use.
- Weapon switching must feel immediate.
- Pickups respawn on timers.

### Player state
- Health.
- Armor that absorbs a defined fraction of incoming damage.
- Ammo per weapon.
- Death → short delay → respawn at valid spawn point.

## Bots
Target 3–5 active bots in the first polished arena.

Bots require:
- Navigation through the arena.
- Enemy acquisition and line-of-sight checks.
- Basic aim error based on difficulty.
- Weapon choice based on range/ammo.
- Item-seeking behavior when health/ammo is low.
- Combat strafing and repositioning.
- Recovery when stuck.
- Three difficulty presets driven by data rather than separate AI code.

Bots need not perfectly reproduce Quake III bot behavior. They must create believable pressure and movement around the arena.

## Match loop
First mode: Free-for-All against bots.
- 10 frag target by default.
- Scoreboard.
- Match timer optional for first milestone.
- Player and bots score frags.
- Match-end panel with restart.

## Arena
One polished original arena is the first content target.

Design requirements:
- Compact enough to encounter enemies frequently.
- At least two height layers.
- Multiple loops rather than one corridor chain.
- At least one risky high-value pickup location.
- Vertical sightline opportunities.
- Rocket-friendly spaces and tighter shotgun spaces.
- No copied Quake map layout.

## Pickups
- Health small / large.
- Armor.
- Ammo.
- Weapons.
- Optional temporary powerup only after core loop is stable.

## UI
- Crosshair.
- Health and armor.
- Ammo and current weapon.
- Frag score / leader information.
- Death/respawn feedback.
- Pause/settings screen.
- Match-end panel.

## Art direction
Original industrial sci-fi arena aesthetic:
- large readable shapes;
- modular metal/concrete kit;
- warm hazard lights contrasted with cool ambient lighting;
- restrained emissive accents;
- strong pickup silhouettes;
- clear navigation landmarks;
- performance-friendly geometry.

Do not reproduce Quake III logos, iconography, map themes, textures, models, or weapon silhouettes exactly.

## Performance target
For the prototype, prioritize stable gameplay and low input latency over expensive rendering. Avoid unnecessary high-poly assets, excessive transparency, and gratuitous dynamic lights.

## Milestone definition of done
A milestone is complete only when:
1. the project launches without fatal errors;
2. the changed feature is exercised in the running game;
3. relevant debug output is checked;
4. major visual work has screenshot evidence;
5. obvious regressions are addressed;
6. the work is committed from its Kanban worktree.

# Pulse Arena — Architecture Contract

## Engine
- Godot 4.x, standard build.
- GDScript unless a task explicitly justifies another language.
- Favor small scenes/resources and composition over deep inheritance.

## Top-level scene shape
Suggested target structure:

`Main`
- `MatchController`
- `ArenaRoot`
- `Actors`
  - `Player`
  - `Bots`
- `Projectiles`
- `Pickups`
- `UI`

The exact tree may evolve, but responsibilities should remain separated.

## Shared contracts

### Damage
All damageable actors should expose a consistent damage entry point such as:
`apply_damage(amount, source, hit_position, impulse, damage_type)`

Do not make weapons know player/bot implementation details.

### Actor query
Player and bots should expose common information needed by weapons and match logic:
- alive/dead state;
- team/id if future modes need it;
- position/aim origin;
- health/armor;
- current weapon;
- death signal/event.

### Weapon contract
Weapons should separate:
- weapon data/resource;
- firing rules/cooldown/ammo;
- hitscan or projectile execution;
- presentation hooks.

Art may replace meshes/VFX without rewriting weapon rules.

### Bot data
Difficulty and behavior tuning belongs in data/resources, not duplicated bot scripts.

### Arena data
Spawn points, pickup points, and encounter landmarks should be nodes/resources that Agent 2 can edit without touching core player code.

### Art boundary
Gameplay scenes may reference placeholder visual slots. Agent 3 can replace meshes/materials/VFX through those slots without editing combat rules.

## Ownership-sensitive files
Only Agent 1 should normally modify:
- `project.godot`;
- global input map;
- autoload configuration;
- common actor/damage interfaces;
- shared core resources.

If another agent needs a shared change, the task should document the requested interface change rather than silently making it.

## Verification architecture
Use Godot MCP Runtime for:
- project launch;
- runtime screenshots;
- simulated input;
- scene-tree inspection;
- live GDScript queries;
- debug output.

Keep test scenes under `game/testing/` and avoid coupling tests to final art assets.

# Role: Agent 1 — Core Gameplay & Bot AI Lead

> “I own the part that must feel right. I build the player, weapons, damage model and bot brain, keep the architecture clean, and I am the person who says whether the merged game is technically healthy.”

## Runtime
Claude Code using the user's Claude subscription. Use the strongest included coding/reasoning model available within the plan.

## Responsibilities
- player controller and movement feel;
- camera/mouse look;
- health/armor/damage interfaces;
- weapons and projectiles;
- bot AI architecture, navigation, combat decision-making;
- respawn/death mechanics;
- common interfaces and shared resources;
- integration fixes after parallel branches merge.

## Explicit non-responsibilities
Do not spend time making final environment meshes, decorative props, final materials, or UI styling. Do not redesign the arena when Agent 2 owns it.

## Quality bar
- Player input must feel responsive.
- No frame-rate-dependent movement logic.
- Bot behavior must be inspectable/tunable through data.
- Core logic must work with placeholder geometry and art.
- Use runtime verification rather than assuming scene/code correctness.

## Completion report
State:
1. files changed;
2. runtime scenarios tested;
3. screenshots/log evidence paths;
4. known limitations;
5. any requests for Agent 2 or Agent 3.
