The art pipeline

Precursor · runs once · output is frozen

0.1 — HardwareRun this on the 4070, not the EVO-X2

This is the one place I'd argue against your instinct, and it isn't about memory. You were right that generation isn't VRAM-bound; SDXL at 1024px doesn't come close to needing 96 GB. The problem with the EVO-X2 is the software stack underneath it.

Strix Halo reports as gfx1151, and that architecture ID decides which precompiled kernels PyTorch can use. Through late 2025 and into 2026 the working setups for it were Linux, Docker or distrobox, built from ROCm nightlies, with an active issue trail about GPU hangs and kernel crashes during diffusion. On Windows it's thinner still. That is exactly the terrain where you told me you've been burned before.

The 4070 runs the boring CUDA path that every tutorial, LoRA trainer and ComfyUI node assumes. For 512–1024px game assets it is the right machine. Let the EVO-X2 keep doing what it's already good at: LLMs in LM Studio.

If you want the EVO-X2 anyway

There is one clean Windows-native path: Amuse (TensorStack, AMD-endorsed). Installer, real GUI, explicitly optimised for Ryzen AI Max+ 395, no Python, no ROCm wrangling. Good for exploration and style hunting.

The catch: it's a walled garden. Limited LoRA and ControlNet support means it can't be your consistency engine. Use it to find a look, then reproduce that look on the 4070 where the ecosystem lives.

0.2 — SoftwareWhat to download

InvokeAI primary UI
The one you live in. Proper installer, gallery and boards, model manager, canvas. Boards map directly onto approve-and-freeze, which ComfyUI has no concept of.
ComfyUI secondary
Add later, only for reference-driven editing workflows and batch runs. Node graphs are visual but they are a second job. Install ComfyUI Manager with it.
OneTrainer LoRA GUI
Desktop GUI for training an SDXL style LoRA. 12 GB is enough for SDXL LoRA training. This is your consistency mechanism.
rembg / BiRefNet cutout
Background removal. Deterministic, runs on everything identically.
ImageMagick cli
Trim, pad, resize, palette quantise. One script, written once, never touched again.
free-tex-packer atlas
GUI atlas packer, exports Phaser JSON hash format directly.
Aseprite optional
Manual cleanup. Raw generation almost never drops in clean, and ten minutes of hand-fixing beats forty re-rolls.

0.3 — ModelsWhat to actually load

SDXL 1.0 workhorse
Default choice. Not because it's the best model in 2026 — it isn't — but because it has by far the deepest LoRA and ControlNet ecosystem, and your problem is control, not fidelity.
Z-Image Turbo drafts
6B, sub-second-ish. Use it for the wide exploration batch in 0.4 where you're throwing away 90% of what you make.
Qwen-Image-Edit consistency
Reference-driven editing. Heavy — this is the one job worth pushing to the EVO-X2 if the 4070 chokes. See 0.4, route B.

0.4 — MethodThe consistency recipe

The thing that has probably bitten you before: consistency does not come from the prompt. It comes from the reference and from freezing every variable that isn't the subject. Prompt-only style matching drifts within a session and falls apart across days.

  1. Explore wide, cheap. Z-Image Turbo, many seeds, junk quality. You're hunting a look, not making assets. Keep 3–5.
  2. Write style-lock.md. Exact model file and hash, sampler, steps, CFG, resolution, negative prompt, a prompt template with one {subject} slot, the palette as hex values, and a fixed sentence describing lighting and camera angle. This file is law.
  3. Build the anchor set — 20–40 images that visibly agree with each other. Then pick a route:
    Route A (stronger): train an SDXL style LoRA on them in OneTrainer. Slower to set up, most reliable thereafter.
    Route B (faster): skip training. Use Qwen-Image-Edit and reframe every request as replacement — "keep this style, change the subject." Consistency comes from the template, not the generation.
  4. Generate the real set in one sitting. Not across days. Settings and model behaviour drift between sessions and you will not be able to tell why.
  5. Log everything to generation-log.csv: filename, seed, prompt, model, settings. Non-negotiable — it's the only way to reproduce or extend the set in three weeks.
  6. Post-process deterministically. One script: cutout → trim → pad to power of two → palette quantise → atlas. Identical treatment for every asset, so nothing looks different for reasons unrelated to the art.

1.201-directions.md — deliberately vague

Four seeds, loose on purpose. The one thing that must not be loose is the axis, or you'll get four flavours of the same idea back.

## Direction A
working title:
prompt:        <1–2 vague lines from you>
must differ on: <named axis>
out of bounds:  <what it can't become>

## …B, C, D — same shape, different axis

# Axes to pick from: player agency vs. luck ·
# tempo · planning depth · spatial vs. resource ·
# solo optimisation vs. reactive pressure

Claude Code then expands each into design/0X-name.md, and every one must contain:

  • Core fantasy, one line
  • Moment-to-moment loop
  • Parameters as numbers, all of them, tunable
  • Feel targets as measurable quantities — input-to-feedback ms, animation durations, decisions per minute, ratio of forced to free moves, turns to first meaningful choice
  • Its own predicted failure mode
  • One falsifiable success signal
  • Asset list, drawn only from /art/approved/

You critique, it revises, two rounds maximum. Then you choose what goes forward — the four it wrote, or your own substitutes, or a mix. Nothing downstream assumes the four survive.

Gate 1 · human approval

Four docs that genuinely differ on their named axis, each with a numeric parameter block, measurable feel targets and an asset list.

02

Implementation

The loop · mechanical gates only

2.1Build order

Shell first, then the test harness, then one mechanic. Not four in parallel — the first one teaches you what your rubric is missing, and you'd rather learn that once than four times.

2.2Gates the machine may check itself

  • Build and typecheck green
  • Playwright drives a full session, N moves, no crash
  • Headless sim over ~10k runs reports: win rate, move-count distribution, dead-state rate, dominant-strategy check
  • Screenshots captured at every named moment
  • Implemented parameters match the design doc's numeric block exactly

2.3The heuristic checklist

Your UI/UX list, applied to captured frames rather than to source code. Legitimate, because these are conformance questions with answers:

  • Contrast and legibility at real device size
  • Is the primary action unambiguous
  • Is current state visible without interaction
  • Does feedback land inside the stated ms window
  • Does the approved sprite still read against its actual background, in its actual placement

You supply the weighting — which items matter most for this game. The model applies the rules; it does not set the priorities.

Gate 2 · the kick-back rule

When an asset fails the readability check, the loop does not regenerate art. It writes the failure to art-requests.md and moves on.

That file goes back to Stage 0 for your approval. Otherwise generation leaks into the loop through the side door and your comparisons stop meaning anything.

2.4The critic pass

  • Runs as a fresh invocation — sees the code and the rubric, never the reasoning that produced the code. Self-critique in the same context just defends itself.
  • Default posture is reject. It must justify a pass.
  • Three passes maximum per prototype. Hard cap, no "until done."
  • Every pass writes a changelog: what changed, which rubric item drove it. This is your early warning for spec drift.
  • Every pass ends with a playable build and a captured GIF, so you can spot-check in sixty seconds without playing.
Gate 3 · mechanical

All checks green, cap not exceeded, build runs, GIF captured, changelog written.

2.5Then you

Play all four in one sitting, randomised order, about thirty minutes. Numbered observations into feel_notes.md. The second loop reads that file and nothing else. Small diffs, re-run the gates, two rounds. Then kill two and go deep on two.

Where this breaks

Check these first when it goes wrong

Art drifts in
Something regenerates mid-loop and you can no longer tell whether the mechanic improved or the sprites just rolled better.
Harness built last
Prototypes end up with different polish levels and you compare juice instead of mechanics.
Convergent briefs
Four variations on one idea. Symptom of a soft axis in 01-directions.md.
Unbounded loop
Endless polishing of things nobody asked about. The cap exists for this.
Rubric as proof of fun
Every box ticked, still no game. Conformance is real work but it is not the same question.
