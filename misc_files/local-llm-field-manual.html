How an LLM actually works

next-token predictiontransformerattention

Strip away everything else and a large language model is autocomplete, taken absurdly seriously. It does exactly one thing: given some text, it predicts what the next little piece of text (a token, entry 02) is most likely to be. It writes one token, sticks it onto the end of the text, and predicts again. Every essay, every code file, every chat reply is produced one token at a time in a loop.

Where does the “prediction” come from? During training (entry 04) the model read trillions of words and slowly tuned billions of internal numbers — its parameters (entry 01) — until its guesses matched real text. In the process it was forced to absorb grammar, facts, coding patterns, and a surprising amount of reasoning, because you can’t reliably predict the next word of a physics textbook or a Python file without modelling what it’s about.

The box in the middle is a transformer — a stack of identical layers, each doing two jobs. An attention step lets every token look back at the earlier tokens and decide which ones matter right now (in “the capital of Finland is…”, the word Finland should matter a lot). A feed-forward step then transforms what attention gathered — this is where most of the stored knowledge sits. Thirty to ninety of these layers run in sequence, and out the top comes a score for every token in the vocabulary.

Running a model locally just means this loop happens on your machine instead of a datacenter. Concretely, you download two things: a big file of numbers (the weights, e.g. a .gguf file — entry 13) and a small program that does the matrix math (an engine like llama.cpp, wrapped by LM Studio or Ollama). Everything else in this manual — VRAM, quantization, t/s, MTP — is about making that loop fit in your memory and run fast.

In practice

Watch the loop with your own eyes: in LM Studio, ask any local model a question and watch the reply stutter out word-fragment by word-fragment. Each fragment you see appear is one full trip through fig 00-A — billions of multiplications per token.

01

Parameters — what the “B” means

B = billiona.k.a. weightsunit of model size

A parameter is one learned number inside the model — a single knob, something like 0.0231 or -1.87. Each one nudges signals up or down as data flows through the layers in fig 00-A. Training is the process of setting all the knobs; the finished model is nothing more than the full list of them. “Weights” and “parameters” mean the same thing in everyday use.

The number in a model’s name — Qwen3.5-9B, Gemma-4-31B, Llama-3.1-70B — is the count of those knobs in billions. More parameters means more capacity to store knowledge and patterns, but also linearly more memory to hold and more math per token, so the “B” is the single fastest predictor of can my machine run this, and how fast.

One caution: parameter count is capacity, not quality. Training data, architecture and post-training improved so fast that a good 2026-era 9B beats a 2023-era 70B on many everyday tasks. Compare models of the same generation by B; across generations, trust benchmarks and your own tests over raw size.

In practice

Quick mental math: parameters × bytes-per-parameter = memory needed. A 9B model at full fp16 precision is 9 × 2 = 18 GB — too big for most GPUs, which is exactly why quantization (entry 15) exists.

02

Tokens & tokenization

subword pieces≈ ¾ of a wordBPE

Models never see letters or words — they see tokens: chunks of text from a fixed menu (the vocabulary, typically 32k–256k entries) learned before training by finding the most common character sequences. Frequent words get their own token; rarer words are assembled from pieces. Every token has an ID number, and those IDs are what actually enter the model.

▁ marks a leading space — “ offline” and “offline” are different tokens. 6 words → 11 tokens here because the rarer words got split.

Rules of thumb for English: 1 token ≈ 4 characters ≈ ¾ of a word, so 1,000 tokens ≈ 750 words. Code and non-English languages (Finnish very much included — long compound words get shredded into many pieces) cost more tokens per idea. Token counts are the currency of everything downstream: context window size (03), KV-cache memory (08), and speed (06) are all measured in tokens.

Tokenization also explains classic LLM blind spots: a model asked how many r’s are in “strawberry” isn’t looking at letters at all — it sees maybe two opaque chunks like ▁straw+berry, and has to remember the spelling rather than count it.

In practice

Local runtimes show token counts everywhere: LM Studio displays them live under the chat box, and llama.cpp logs prompt eval: N tokens. Paste the same paragraph in English and Finnish and compare the counts — the difference is the tokenizer at work.

03

Context window

unit: tokensa.k.a. ctx / n_ctxworking memory

The context window is the maximum number of tokens the model can consider at once — its entire working memory. Everything must fit inside it: the system prompt, the whole conversation so far, any pasted files, and the reply being written. The model has no memory outside this window; “remembering” earlier chat is literally re-reading it on every single token.

Two catches for local use. First, spec-sheet numbers are maximums: many 2026 models advertise 128k–256k, but you choose the actual size at load time, and bigger windows cost real memory (the KV cache, entry 08) and slow down the initial prompt-reading pass. Second, quality degrades before the limit — models are noticeably better at using the start and end of a huge context than the middle.

In practice

In LM Studio the context length is a slider in the model-load settings; llama.cpp uses -c 32768. A sane default for chat and coding on a single GPU is 16k–32k. Raise it only when you actually paste big things — every extra token of window is VRAM you can’t spend elsewhere.

04

Training vs inference

learning vs usingyou run inference

Training is setting the knobs: show the model trillions of tokens, compare its next-token guess to the real next token, and nudge all the parameters slightly toward the right answer (gradient descent), repeated quadrillions of times. It needs thousands of datacenter GPUs for weeks or months and is the expensive part labs pay for. The output of all that effort is just the weights file.

Inference is using the knobs: load the finished weights, freeze them, and run the fig 00-A loop on your prompt. Nothing is learned — the model that finishes your chat is bit-for-bit identical to the one that started it. Running LLMs locally means running inference; the only training hobbyists commonly do at home is light fine-tuning (entry 10).

Training (the lab’s job)

  • input · trillions of tokens of text
  • hardware · 1,000s of GPUs, months
  • weights · constantly changing
  • cost · $10M–$1B+ per frontier run
  • output · the weights file

Inference (your job)

  • input · your prompt
  • hardware · one PC / Mac, milliseconds–seconds
  • weights · frozen, read-only
  • cost · electricity
  • output · tokens on your screen
In practice

This split is why “open-weights” releases matter: when Qwen, Gemma or Llama publish weights, the billion-dollar part is done and gifted to you — the part left for your machine is comparatively tiny. It’s also why your chats can’t “teach” a local model anything across sessions: inference never writes to the file.

05

VRAM, RAM & GPU offloading

unit: GBn_gpu_layersunified memory

To generate each token the hardware must read essentially every parameter from memory (see entry 06 for why that dominates speed). So the first question of local AI is brutally simple: where do the weights sit? Three tiers, from fast to slow: VRAM — memory on the GPU, huge bandwidth (350–1,800 GB/s), scarce; system RAM — plentiful, but ~50–120 GB/s through the CPU; disk — if the model spills here, it’s effectively unusable.

When a model doesn’t quite fit, engines can offload: keep as many transformer layers as possible in VRAM and run the remainder from system RAM on the CPU. It works — but speed collapses toward the slowest link, so a 90/10 split can still cut your tokens-per-second in half. Apple Silicon sidesteps the split entirely: its unified memory is one pool shared by CPU and GPU, which is why a 64–128 GB Mac quietly runs models that embarrass much pricier discrete GPUs.

In practice

LM Studio shows a green/orange/red “will it fit” estimate before you even download a file, and exposes GPU offload layers as a slider. If generation feels inexplicably slow, check whether the runtime silently offloaded — the fix is usually a smaller quant (entry 15), not a smaller model.

06

Tokens per second (t/s)

a.k.a. tok/s, tpsmemory-bandwidth boundprefill vs decode

t/s is the speed rating of local AI: how many tokens the model emits per second. For feel: 5 t/s is a slow reader you wait on, 20 t/s is comfortable chat, 60+ t/s is instant-feeling, and coding agents happily eat hundreds. The surprising part is what limits it — not GPU compute, but memory bandwidth, because generating one token means streaming (roughly) the entire weights file from memory through the chip.

Back-of-envelope speed limit

  • rule of thumb · t/s ceiling ≈ memory bandwidth ÷ model size in memory
  • RTX 4090 (1,008 GB/s) ÷ 5.5 GB model · ≈ 180 t/s ceiling
  • RTX 3060 (360 GB/s) ÷ 5.5 GB · ≈ 65 t/s
  • M4 Pro Mac (273 GB/s) ÷ 5.5 GB · ≈ 50 t/s
  • CPU + DDR5 (≈ 90 GB/s) ÷ 5.5 GB · ≈ 16 t/s
  • real world · expect ~50–80% of the ceiling (overheads, KV cache reads)

This one formula explains most local-LLM folk wisdom: why halving a model’s bytes via quantization roughly doubles speed, why a used 3090 with fat bandwidth beats some newer cards, why CPU-only inference of big dense models crawls, and why MoE (entry 12) and MTP (entry 16) feel like cheating — they reduce, or amortize, the bytes read per emitted token.

One more distinction worth knowing: reading your prompt (prefill / “prompt processing”) is a different phase from writing the answer (decode). Prefill crunches many tokens in parallel and is compute-bound — often thousands of t/s on a GPU — while decode is the bandwidth-bound one-at-a-time loop above. That’s why a huge pasted document pauses briefly before the first word, then streams normally.

In practice

Every runtime reports both numbers after a reply (LM Studio shows them under the message; llama.cpp prints prompt eval and eval rates). When benchmarking models against each other, keep quant, context size and GPU-offload identical — otherwise you’re measuring your settings, not the model.

07

Temperature, top-p & top-k

samplingthe randomness dials

The model outputs a probability chart (fig 00-B); the sampler decides which bar to pick. Temperature reshapes the chart before picking: below 1.0 it sharpens the peaks (the favourite wins almost every time — predictable, focused, sometimes repetitive), above 1.0 it flattens them (underdogs get real chances — creative, varied, eventually unhinged). Temperature 0 means “always take the top bar”: the same prompt then yields the same answer every time.

The fences: top-k keeps only the k highest bars (e.g. k=40) before sampling; top-p (“nucleus”) keeps the smallest set of bars whose combined probability reaches p (e.g. 0.9) — adaptive, so it keeps 1 candidate when the model is sure and 30 when it isn’t. They exist because at higher temperatures the thousands of tiny-probability junk tokens collectively add up to a real chance of derailment.

In practice

Good defaults: temp 0.7, top-p 0.9 for chat; drop toward temp 0.2–0.4 for code and data extraction; raise toward 1.0–1.2 for brainstorming. If a local model loops or rambles where the cloud version didn’t, suspect the sampler settings before blaming the model — runtime defaults vary and model cards often recommend specific values.

08

KV cache

key/value cachewhy long chats eat VRAM

Attention (entry 00) lets each new token look back at all earlier tokens. Done naively, that means reprocessing the entire conversation for every single generated token — quadratic, ruinous. The fix: the first time each token is processed, the model saves the two vectors attention needs from it (its Key and Value) and never recomputes them. That stash is the KV cache.

Consequences you’ll actually feel: the cache is why token #500 generates as fast as token #5 (no re-reading), why VRAM use creeps up during long sessions, and why doubling your context window setting reserves real gigabytes even before you use them. Modern architectures shrink it with tricks like grouped-query attention (several attention heads sharing one K/V set), and runtimes let you store the cache itself at 8-bit with little quality loss.

In practice

If a long coding session slows down or OOMs: start a fresh chat (empties the cache), lower the context slider, or enable KV-cache quantization (q8_0 is the safe pick — in LM Studio it’s under the model-load “advanced” panel, in llama.cpp --cache-type-k q8_0 --cache-type-v q8_0).

09

Base vs instruct models

-instruct / -it / -chatchat templatesystem prompt

Fresh out of pre-training, a base model is a pure next-token engine with no concept of “you” and “me”. Ask it “What is quantization?” and it may reply “What is distillation? What is pruning?” — because a list of questions is a statistically plausible continuation. It’s a magnificent autocomplete, not an assistant.

An instruct model (suffixes -instruct, -it, -chat) is that same base after post-training: fine-tuned on question→answer conversations and preference-tuned (RLHF and friends) to follow instructions, converse in turns, and refuse the worst stuff. This is the kind you want in a chat UI, and it’s what runtimes assume by default.

Turn-taking works through the chat template: special tokens that wrap each speaker’s text so the model can tell who said what. The UI hides this scaffolding, but it’s always there — including the system prompt, an invisible first message that sets persona and rules:

## what the model actually receives (Qwen-style template) <|im_start|>system You are a concise assistant for game economy design.<|im_end|> <|im_start|>user What does ARPDAU stand for?<|im_end|> <|im_start|>assistant Average Revenue Per Daily Active User — total daily revenue ÷ DAU.<|im_end|>
In practice

Symptoms of a wrong or missing template: the model answers as you, continues your question instead of answering, or leaks tags like <|im_end|> into replies. GGUF files carry the correct template inside them, so modern runtimes get this right automatically — it mostly bites when APIs or scripts assemble prompts by hand. Grab a base model only for raw completion tasks and fine-tuning projects (entry 10).

10

Fine-tuning & LoRA

post-training at homelow-rank adaptersQLoRA

Fine-tuning is continuing a model’s training on your own examples to change its behaviour — your studio’s tone of voice, a data format it must always emit, a niche domain. It shifts style and skills reliably; it’s a poor tool for injecting facts (for “answer from my documents”, retrieval/RAG-style setups work better). Full fine-tuning updates every parameter, which for a 9B model means datacenter-class memory — out of reach at home.

LoRA (Low-Rank Adaptation) is the trick that made home fine-tuning real: freeze all the original weights, and next to each big weight matrix train a pair of skinny matrices whose product is the change you want. Those adapters are typically <1% of the model’s size, so they train on a single consumer GPU and ship as tiny files you can stack or share. QLoRA pushes further by holding the frozen base in 4-bit (entry 15) while training the adapters — a 9B fine-tune inside ~8–12 GB of VRAM.

In practice

The usual home pipeline: a few hundred–few thousand example conversations in JSONL → QLoRA with a library like Unsloth or Axolotl on a 12–24 GB GPU (or rented cloud GPU) for minutes–hours → merge → export to GGUF → load in LM Studio like any other model. Before committing, always test whether a good system prompt plus examples gets you 90% of the way — it often does, for free.

11

Distillation

teacher → studentwhy small models got good

Distillation trains a small “student” model to imitate a big “teacher”. Instead of learning only from raw internet text, the student learns from the teacher’s behaviour — either its full probability charts (fig 00-B, the “soft targets”: not just the answer is Helsinki but Helsinki 93.7%, the 2.9%…, which carries far more signal per example) or, more commonly today, from large synthetic datasets of questions, answers and step-by-step reasoning that the teacher writes.

This is the open secret behind small models punching above their weight class: nearly every strong 1–9B model you can download was taught, at least partly, by a frontier-scale system. It’s also why families ship in size ladders (0.6B → 397B in one release) — one teacher, one recipe, many students, so you can pick the largest size your VRAM allows and get consistent behaviour.

In practice

You’ll meet the word on model cards: “distilled from…”, or names like DeepSeek-R1-Distill-Qwen-7B — reasoning behaviour from a giant, transplanted into a 7B body. When a tiny model narrates chain-of-thought suspiciously well, distillation is why.

12

Mixture of Experts (MoE)

A3B = ~3B activesparse modelsvs “dense”

In a standard (dense) model, every token flows through every parameter. A Mixture-of-Experts model replaces each layer’s big feed-forward block with a panel of smaller parallel blocks — the experts — plus a tiny router that, per token, activates only the best-suited few (say 2–8 of 64+). The result: the knowledge capacity of a huge model, the per-token compute of a small one.

For local use that trade is unusually sweet if you have the memory: all experts must be loaded (VRAM/RAM pays for total parameters), but each token only reads the active slice, so t/s tracks the small number. A 35B-A3B can feel nearly as fast as a 3–4B dense model while being far smarter. MoE + unified-memory Macs and MoE + partial CPU offload are particularly happy pairings, since capacity is what those setups have and bandwidth-per-token is what they lack.

In practice

Reading model names: Qwen3.6-35B-A3B, Qwen3.5-122B-A10B, Mixtral 8x7B (8 experts × 7B, the 2023 original that popularized the idea). When comparing an MoE against a dense model, compare active params for speed expectations and total params for the fig 05-A memory check.

13

GGUF, llama.cpp & runtimes

.ggufLM Studio · Ollamasafetensors

GGUF is the file format of local AI: one self-contained file holding the quantized weights plus everything needed to run them — tokenizer, chat template, architecture metadata. Download it, point an engine at it, done. It’s the native format of llama.cpp, the open-source C++ engine that actually executes the math on almost every consumer setup (NVIDIA, AMD, Apple Silicon, plain CPUs).

Most people don’t drive llama.cpp directly; they use a runtime wrapped around it. LM Studio: desktop app — model browser, chat UI, load-settings panel, local API server. Ollama: terminal-first — ollama run <model>, popular for scripting and self-hosted services. Others (Jan, Koboldcpp, llama-server’s own web UI) sit on the same engine. The other format you’ll see, safetensors, holds full-precision weights for the Python/GPU-server world (Transformers, vLLM) — that’s what GGUFs are converted from.

14

Speculative decoding

draft + verifyfree speed, same output

The decode loop’s bottleneck (entry 06) is reading the whole model once per token. But verifying several proposed tokens in one pass costs barely more than generating one — the expensive memory read is shared. Speculative decoding exploits that: a small, fast draft model guesses the next few tokens, then the big target model checks them all in a single forward pass, keeping the guesses up to the first mistake.

The speedup depends on the acceptance rate — how often the small model guesses what the big one would say. Predictable text (code, boilerplate, lists) accepts beautifully and can run ~1.5–2.5× faster; wild creative prose accepts less. Costs: the draft model occupies extra memory, and it must share the target’s tokenizer — which usually means picking a tiny sibling from the same family (a 0.6B drafting for a 27B).

In practice

In LM Studio, speculative decoding lives in the model-load settings: pick a compatible small draft model next to your main one. In llama.cpp it’s -md <draft.gguf>. If juggling two files sounds clumsy — agreed, and that’s exactly the itch MTP (entry 16) scratches by building the drafter into the model.

15

Quantization

Q4_K_M and friendsbits per weightthe great enabler

Quantization stores each of the model’s billions of numbers with fewer bits. Training uses 16-bit precision (~2 bytes per parameter, billions of finely-tuned decimals like 0.02317); for inference, that precision is mostly wasted. Quantization rounds weights onto a coarser grid — 8, 6, 4, even 2 bits — and keeps a small scale factor per block of weights so the grid stays anchored to the right range. The insight that created the entire local-LLM hobby: models barely mind. Sloppier individual weights largely cancel out across billions of operations.

Decoding the cryptic suffix on every GGUF file, using Q4_K_M: Q = quantized · 4 = ~4 bits per weight (the headline compression) · K = the modern “k-quant” scheme — weights packed in small blocks, each block carrying its own scale, which preserves far more fidelity than one global grid · M = medium mix: the layers most sensitive to damage (embeddings, attention output) are quietly kept at higher precision, S/M/L variants trading a few hundred MB for care. You’ll also meet IQ quants (IQ4_XS…): built using an importance matrix from calibration text so the bit budget goes to the weights that matter most — the strong choice below 4 bits.

In practice

Default playbook: take Q4_K_M. Spare VRAM after the fig 05-A check? Step up to Q5_K_M/Q6_K — or better, a bigger model at Q4. Squeezed? IQ4_XS, then Q3_K_M, accepting visible trade-offs. Q8_0 is for “I want it near-lossless and have the room”; below Q3 is for emergencies. And note it’s all inference-side — the quantized file is made once from the fp16 original; your machine just runs it.

16

Multi-Token Prediction (MTP)

self-speculativebuilt-in draft heads2026’s speed unlock

Everything so far assumed the loop’s iron law: one forward pass, one token. MTP bends it. An MTP model is trained with small extra prediction heads that, from the same internal state, also guess token n+2, n+3… ahead. Originally (DeepSeek-V3, late 2024) this was a training trick — forcing the model to plan ahead makes it learn better — but the heads pay off twice: at inference they become a built-in drafter for self-speculative decoding. Draft with your own heads, verify with your own body: speculative decoding (entry 14) with no second model to download, load, or keep in VRAM.

The catches: the heads must be baked in at training time — a runtime can’t bolt MTP onto an ordinary model, so it only works on checkpoints shipped with heads (Qwen 3.5/3.6’s -MTP GGUFs across the ladder, Google’s separate Gemma 4 MTP variants, DeepSeek V3-family). Gains are biggest exactly where local users hurt most — bandwidth-starved decoding of dense models — and, as with all speculation, on predictable text like code. Support went mainstream in 2026: llama.cpp merged it (behind a --mtp flag, still maturing) and LM Studio exposed it as a load-time toggle from 0.4.14.

In practice

LM Studio recipe: update to ≥0.4.14 (llama.cpp engine ≥2.15.0) → download an MTP build, e.g. Qwen3.5-9B-MTP → flip the MTP switch in the load settings → compare t/s on the same prompt with it off. Leave ~2 GB of memory headroom, and if you’re tuning llama.cpp directly, try draft lengths around --spec-draft-n-max 2 and adjust from there — the optimum is hardware-dependent.

And with that, the loop from entry 00 comes full circle: parameters give the model its mind, quantization fits that mind into your VRAM, and MTP makes the loop itself run faster than one-token-per-turn. That’s the whole stack.
